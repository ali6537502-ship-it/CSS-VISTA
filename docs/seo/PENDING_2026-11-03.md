## Confirmed privacy-control issue and correction

On a fresh live `/cookie-policy` document, the footer's Privacy & Cookie Settings button only navigated to `/cookie-policy#managing-cookies` when Google's API was unavailable. The resulting page still had no Google API and gave no status or usable fallback from that control. The [baseline browser record](evidence/2026-11-03/privacy-control-baseline.json) records the URL, absent API and absence of advertising loaders. The previous source also called the API directly without its readiness queue.

[Google's official messaging API documentation](https://developers.google.com/funding-choices/fc-api-docs), read on 3 November, documents `callbackQueue` with `CONSENT_API_READY` for consent API calls. It explicitly warns that a revocation link has no effect if the API has not loaded. This supports a source-level readiness/fallback repair; it does not prove a Google policy violation or the cause of an AdSense rejection.

The new control:

- Queues only an explicit user request until Google's API is ready.
- Reports a request as requested, not as proof that a message displayed or consent changed.
- Times out with a clear unavailable state and homepage/cookie-help links.
- Cancels expired, unmounted and navigated-away requests, preventing a late callback from opening a message unexpectedly.
- Loads no advertising or CMP script, changes no eligibility policy, stores no user data and changes no publisher/account configuration.

Files: `src/lib/privacyChoices.ts`, `src/components/PrivacyChoicesButton.tsx`, `src/components/TrustFooter.tsx`, `tests/privacyChoices.test.ts`, `tests/browser/privacy-choices.mjs`, and package test commands. Both normal and focused-study footers use the same control. Navigation remounts it through the existing router location key. Existing accounts, resources, pauses and source content remain intact.
