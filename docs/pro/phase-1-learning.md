# Phase 1B: preparation, writing and AI-accounting foundations

Implemented for review alongside Phase 1A in draft PR #78. No merge, production migration, collection launch or live AI use is authorized by this increment. It gives the common account useful saved preparation settings and writing versions. It does not claim that the complete My CSS Attempt planner, Grammar upgrade, Expression Lab, OCR or Précis Lab is finished.

## Owned preparation and writing

`/account/preparation` reuses native authentication, full-profile eligibility and `AccountPage`. New attempt settings are free account-owned records: CSS target year, optional student target date, preparation stage, daily minutes and an optional-subject shortlist drawn from `public/fpsc-syllabus.json`. Target dates are **student targets**, never official announcements. The shortlist validates IDs, uniqueness, size and maximum 600 marks; it is explicitly **not a certified FPSC subject combination**. The official source PDF again returned HTTP 503. Complete compulsory/religious-option mapping and application grouping validation require verified source work in the later attempt phase. Existing profile choices, selector, planner, syllabus states and browser progress are neither imported nor overwritten.

Sentence, paragraph and précis writing can be explicitly saved against an owned attempt. Saving creates an immutable text version, hash and deterministic Unicode word count. Revisions append; they do not overwrite earlier wording. Counts treat internal apostrophes/hyphens as one word and are a software convention, not a claim about official marking. Up to 20,000 characters can be stored; this storage allowance does not establish an AI-evaluation allowance.

`student/learning.php` requires native session, actual profile eligibility and ownership; POST also validates CSRF, expected user, bounded JSON, strict fields and the established rate limiter. `attempt_save` and `writing_save` use UUID request identity, canonical payload hash and persisted result. A per-account row lock serializes mutations. Same identity/body returns the existing result; a changed body conflicts. Optimistic `expected_version` rejects concurrent changes. IDs, account ownership, date provenance and version numbers cannot be assigned arbitrarily by the client. A saved writing record retains its original attempt and type.

GET supports owned attempts, records and versions; overview histories paginate 50/page. Prior writing and settings remain readable and revisable after Pro expiry. No subscription interval owns or deletes learning records. There is no automatic backfill, destructive reset, invented skill score or artificial completion percentage.

The editor reuses existing draft storage with a versioned **user-scoped** key (`cssvista:draft:learning:v1:USER:RECORD`). New anonymous/legacy drafts are not assigned to an account. Browser drafts are local; explicit Save creates the account copy. Keyed account components and before/after expected-user checks prevent stale responses from showing another account's records. Request retry caches contain UUID/hash only, not writing. A restored draft keeps its base version; the user reviews a changed saved version before explicitly adopting that base. Save failure preserves input.

## AI operation and accounting contract

`013_learning_foundations.sql` adds preparation attempts, writing records/versions, idempotent learning saves, daily usage, AI operations and anchored writing findings. SQL/PHP mirrors are tested. The schema is additive, shares existing users and Pro memberships, and follows existing guarded schema initialization outside business transactions. No migration runs against production during this task.

AI policy buckets initially configure précis 2, paragraph 5, sentence 15, tutor 20, Current Affairs 10 and Maths 10. Handwriting/OCR are unavailable until separately decided. Policies are server configuration; the browser receives actual limits. Reading, quizzes, planner use and saving writing reserve no allowance and make no provider call.

Only internal version-bound paragraph/sentence operation functions are wired for this foundation; **there is no public AI evaluation POST endpoint**. Other buckets are policy preparation, not available services. Future feature endpoints must authenticate, validate CSRF/profile/ownership and bind their exact permitted context before using these functions. Reservation also checks saved-profile eligibility, active Pro and private configuration. Owned status/result retrieval does not require active Pro. Full-answer/essay/OCR scopes are rejected.

Lifecycle:

1. Stable user/request UUID + feature + owned immutable version/hash identifies an operation. A matching retry returns the prior pending/terminal operation, including after expiry; mismatched intent conflicts.
2. A short account-serialized transaction checks `used + reserved < configured limit` and accepted-attempt cap `3 × limit`, fixes the reservation's **Asia/Karachi date**, and saves operation/reservation together. Failed attempts cannot create unlimited provider-cost opportunities.
3. Dispatch claims the reserved operation once; no database lock spans network I/O. Preflight failure releases an unstarted reservation and records no provider dispatch. Later visits do not re-dispatch in-flight, unknown or terminal operations.
4. Known completion validates structured output and exact submitted excerpts, then atomically stores useful findings/result and consumes one successful allowance. Known rejection or invalid terminal output releases the successful allowance but retains dispatch and reported usage. Missing tokens/cost are unavailable, never fabricated zero values.
5. Transport failure/ambiguous server outcome holds the reservation as **unknown**. A client timeout does not prove provider failure. No automatic provider retry, alternate model or provider fallback exists.
6. Completion uses the original bucket even across midnight and preserves results after subscription expiry. Duplicate terminal completion cannot duplicate findings or allowances.

`server/bin/ai-operation-sweep.php` is CLI-only and **not scheduled/deployed here**. It conservatively releases a reservation older than five minutes only if never dispatched, and marks an old in-flight dispatch unknown without releasing its allowance. It never repeats a provider request, deletes student work or assumes an unknown billed outcome failed. A future accepted-result recovery mechanism must verify actual provider outcome before resolving an unknown operation. That provider-specific recovery and real hosting behavior must be verified before enabling any live feature.

## Configurable primary client and provider limits

Official [Responses create reference](https://developers.openai.com/api/reference/resources/responses/methods/create) was read on 7 October 2026: structured output under `text.format`, input/output/cached token reports and response status are documented. The Phase 0 verified public model designation remains `gpt-6-luna`; actual account access, image capabilities, pricing, limits and deployment transport remain **unverified**. No OpenAI credential is supplied in this workspace.

`_ai_openai.php` is server-only, configurable and disabled by default. One bounded HTTPS POST to the official Responses endpoint, verified TLS, no redirects, no automatic retry, no browser provider calls, no tools, no complete account history and `store:false`. It requests bounded English feedback using a strict schema and learning hints, rather than full-answer marks or replacement prose. The response is still checked server-side for shape, allowed codes/severity and literal excerpt anchors.

Private configuration needs enabled/approved/model-verified flags and a private API key before internal reservation can accept real work. This alone does not publish an action endpoint. Paragraph dispatch is capped at one paragraph/450 words; sentence at 80 words. Input limits and three-attempt abuse accounting are implementation policy for the future constrained scope, not an already launched purchase promise. Précis needs source passage/rubric binding before wiring; tutoring needs feature-specific verified context; OCR needs confirmed-version, retention and accounting rules. No image is accepted or stored in this step. Estimated costs remain null until a reliable verified pricing policy is configured.

## Member/admin reporting

`/account/ai-usage` GET uses the real account's daily buckets and owned operation history, including saved feedback after expiry. It explicitly states live assistance is unavailable. `student/ai-usage.php` rejects POST; no UI click performs an evaluation.

The existing owner/TOTP workspace includes AI usage reporting, protected by the same server session. `admin/ai-usage.php` reports Pakistan-day/month accepted operations, dispatches, success/failure/pending, reported token totals and dispatches lacking reports. It groups features and the top 20 accounts by dispatches; no student writing or payment proof enters the usage view. Calls per Pro user use distinct credited periods overlapping the reporting window as denominator, with unavailable average if no such member exists. Cost remains explicitly unavailable. No complimentary grants are invented.
