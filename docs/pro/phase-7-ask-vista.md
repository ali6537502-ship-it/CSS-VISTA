# Ask VISTA — Phase 7

Implemented for review on draft PR #78. Production, live provider calls and payment collection remain unchanged. This is scoped contextual help; planner/readiness integration and the verified Pro content migration remain Phases 8 and 9.

## Learning flow and approved contexts

`/account/ask-vista` reuses native authentication, complete-profile eligibility, preparation attempts and the account shell. Students select an owned attempt, an existing learning source and one help mode: explanation, misconception, hint or understanding check. Saved questions/replies and the source snapshot are account-linked, readable on another signed-in device and retained after Pro expiry or source unpublication. Continue learning returns to the relevant route, including the selected Grammar day/Précis chapter and attempt. Focused links are provided from Grammar, Précis, published Current Affairs, preparation settings and the AI usage report.

Available contexts are deliberately source-limited:

- 126 existing authored Grammar rule sections, generated by `scripts/tutor/export-grammar.mjs`; source parity is checked. Quiz solutions and correction answer keys are excluded. The authored course and its existing storage remain intact.
- Selected instructional chapters of the owner-supplied Précis handbook. The pending official examination framework, full-model chapters and appendices are excluded. This does not certify the handbook as official examination rules.
- Published, active native Current Affairs stories, labelled with their edition date and original source attribution. Unpublished/future records, unusable attribution and overlong contexts are unavailable. Reading an accepted historical snapshot remains possible after the current story changes or is unpublished.
- Three original Maths concept notes: percentage, arithmetic mean and equivalent ratios. Their practice calculations are deterministic. This is not a replacement Maths course or an authentic past-paper question bank.
- Existing repository syllabus headings, labelled topic maps. A heading establishes scope, not a definition or current official eligibility rule. Insufficient context must produce an honest limitation.

The existing broader issue files/86-topic content have not been recertified or migrated here. No claim is made that every topic has a verified tutoring source. That source-verification work remains part of the later content phase; existing public content is preserved.

## Boundaries and immutable requests

Server-side requests accept one 8–1,000-character question, at most 150 words, and a server-selected source of at most 16,000 characters. Full-answer/essay generation or marking, and changes to human mentor marks, are excluded. Obvious excluded requests are rejected before reservation; the prompt also covers reworded requests and injection attempts. The provider receives only the selected source, question, intent, at most one completed prior question/reply from the same owned attempt/source, preparation stage and daily minutes. It receives no account identifier or entire history. Student/source/prior text is untrusted data, not instructions. `store:false`; no browsing/tools, model fallback or automatic provider retry.

Migration `019_scoped_tutor.sql` adds `tutor_requests`, linked to the existing operations/accounting tables. The snapshot hash canonicalizes JSON key order, preserving validity after MySQL normalization. Reserved inputs are immutable and checked before dispatch and settlement. Source changes reject fresh requests with a stale hash. Accepted replay returns the original operation, including after membership expiry. A previous exchange must belong to the same student, attempt and unchanged source and must be completed. Tutor replies never create writing findings, mentor results, course progress or readiness claims.

Outputs have a strict shape, a 350-word total bound, at most three steps and literal source quotations. Invented quotations, arbitrary URLs, explicit student scores and malformed results fail validation. Insufficient-context/out-of-scope replies must state their limitation without teaching steps. Exact quotations and these checks constrain scope; they do not independently prove factual entailment or model reliability. Real-provider adversarial/source-accuracy calibration remains required before launch.

## Quotas and recovery

The existing shared ledger remains authoritative: general tutoring uses `tutor` (default 20/day), Maths help uses `maths` (10/day), and dated Current Affairs help uses `current_affairs` (10/day). Limits are private server configuration; zero disables a bucket. Karachi midnight determines the original reservation date. Lessons, source previews, saved history, fixed checking and ordinary calculations make zero provider calls.

Account locks serialize reservations. Matching request IDs replay the original receipt; identical accepted/pending/successful intent also aliases the existing operation even with a new request ID. Different work or notice/source versions cannot reuse a receipt. Bounded accepted attempts prevent unlimited rejected/malformed retries. Known failures release the successful allowance while preserving attempt/cost evidence. Ambiguous transport or unresolved provider states remain reserved and cannot be blindly sent again. Shared maintenance handles stale undispatched/in-flight operations with the existing rules.

Before submitting, the browser saves the short request body and ID to account-specific, versioned **sessionStorage**. Storage failure stops submission. A lost response leaves a recovery panel: GET by owned request receipt sends no provider request. Only a confirmed missing receipt offers explicit retry with the same identity or editing of the unaccepted question. Accepted reserved work offers explicit resume; an unknown outcome offers status reading only. The session recovery copy is not a cross-device unsent draft. Accepted history is stored on the server.

## Private configuration and release boundaries

Live help defaults off. In addition to shared AI configuration, it requires `CSSV_TUTOR_ENABLED=1`, a valid `CSSV_TUTOR_POLICY_VERSION` and a 30–3,000-character `CSSV_TUTOR_PROCESSING_NOTICE`. Acceptance binds both version and SHA-256 of the version plus actual notice, so same-version notice changes require fresh review. No real key or approved launch notice was added. The disabled interface states the actual availability.

Official OpenAI documentation was checked on 2026-10-08: `https://developers.openai.com/api/docs/models/gpt-6-luna` identifies `gpt-6-luna` and supports Responses/structured outputs. `https://developers.openai.com/api/reference/resources/responses/methods/create` documents the bounded request format. This verifies the documented identifier, not this application's provider account access, pricing, limits, billing or response quality. Those remain unverified; no substitute model or paid provider call was used.

An authorized production release must use the existing native Hostinger workflow, apply additive migrations in order, preserve private configuration/storage and test the owned flow with actual provider access and approved disclosure. Do not enable live help or collection by merely merging this code. Operational rollback disables the tutor flag while retaining accepted exchanges and ledger history; never drop records to roll back.

## Validation

Pure tests cover source/hidden-model isolation, deterministic Maths, strict output/evidence bounds, safe refusal, minimal provider data, canonical snapshots and SQL parity. Native disposable PDO tests cover authentication/profile/CSRF/account ownership, eligibility, quotas and races, aliases/replay, changed sources/notices, one-parent context, known/unknown failures, original Karachi buckets across expiry, disabled/corrupt preflight and preserved history. Synthetic transport verifies no database transaction is held while sending. It cannot make an external provider call and is unavailable outside CI with the labelled disposable database.

The HTTPS browser flow checks actual native accounts, disabled zero-call reading, revised disclosure acceptance, committed-response-loss recovery, contextual follow-up, return links, separate Maths accounting, unknown status without repeat dispatch, second-device/expiry history and 320/390/768/1440 layouts. Normal lint, type checking, full regression tests and the strict Hostinger build also apply.
