# Phase 2: one-page handwritten paragraph workflow

Implemented for review on the existing foundations branch/draft PR #78. No production migration, launch, payment collection or external model call occurs in this increment. Existing public/free features and Grammar source/progress remain intact. This implements the permitted handwriting journey with labelled disposable-provider tests; it does not claim that real extraction accuracy, account capability or Hostinger cleanup has been verified.

## Student journey and authority

`/account/handwriting` reuses the native account, full-profile gate and `AccountPage`, with a contextual link from My Preparation. A member previews a JPG/PNG/WebP locally, chooses an owned preparation attempt, reviews the current processing notice and explicitly uploads. The original filename is never used or persisted. Uploading makes no provider call.

The workspace uses a graphite/indigo workflow header, current-stage indicators, real daily allowance data, a keyboard-accessible native picker with drag/drop and removable local previews, and side-by-side source/transcription panels on desktop. Mobile stacks the panels. The visual refresh is confined to handwriting components; shared account pages and backend rules are unchanged.

The native workflow is upload → extraction → editable transcription → saved corrections → explicit confirmation → confirmed-text feedback → saved findings → independent rewrite. Only one page and one English paragraph are permitted. Images/text are untrusted content, never instruction authority. No full essay/subjective-answer evaluation, examination marks or polished replacement paragraph is introduced.

Persisted states: `uploaded`, `extracting`, `awaiting_confirmation`, `confirmed`, `evaluating`, `completed`, `unreadable`, `extraction_failed`, `evaluation_failed`, `outcome_unknown`, `image_expired`. States follow persisted operations and immutable versions rather than disconnected frontend booleans. Pending requests can be revisited; refresh/status polling never starts a provider call. Unknown outcomes retain reservations and do not offer a blind provider retry.

Every read/preview/mutation derives the user from the existing session and checks ownership. POST also checks CSRF, expected user, strict payloads, input bounds and native account/network rate limits (60 writes/hour). New uploads, extraction and evaluation require actual active Pro and configured readiness. Corrections/confirmation and saved-history retrieval for previously accepted pages remain available after expiry; accepted dispatched work can finish after expiry. There is no second account or subscription-owned learning dataset.

## Private image handling and retention

The server validates actual MIME, bytes and dimensions, then fully decodes using GD. Supported input codecs are JPEG, PNG and WebP; GD/Fileinfo/EXIF/CURL and private storage are checked before readiness. JPEG camera orientation is applied before re-encoding to JPEG. Re-encoding removes EXIF, original metadata and trailing payloads. The PHP memory budget is checked before decode.

Default technical bounds: source/normalized image ≤5 MiB, edge 320–4096 px, ≤12 MP, one paragraph ≤450 software-counted words/6000 characters. These are bounded implementation limits, not official exam rules. At most three unconfirmed/unexpired raw uploads can coexist per account. Generated files use owned UUID paths, 0600 file/0700 directory permissions and the existing storage root outside the public webroot. Symlink/outside-root anomalies fail closed. Raw paths, content and original filenames do not enter ordinary logs or general admin usage reporting.

`student/handwriting-image.php` streams only the current user's unexpired, unconfirmed temporary image, with no-store, nosniff and sandbox headers. Confirmation atomically retires image availability by fixing its expiry at confirmation, then attempts deletion. If deletion fails, the reference remains for cleanup; correcting the text cannot resurrect image availability. A deleted image is never needed for confirmed-text evaluation. Expired/unreadable images are unavailable and cleaned without deleting saved wording/findings.

`server/bin/handwriting-maintenance.php` wraps the CLI-only `public/api/_handwriting_maintenance.php`, which ships as `dist/api/_handwriting_maintenance.php` with the established Hostinger artifact. Both reject HTTP execution. The packaged runner uses the existing private-config resolver; configure the cron with the actual release path and private configuration, never guessed server paths. It conservatively sweeps abandoned operations, reconciles failure/unknown workflow state, deletes expired/retired images and removes generated orphan staging files older than 24 hours. Deletion failures retain references for a later safe retry. It does not delete payment proofs, old educational results or unrelated private files, and never re-dispatches. Schedule it at least every five minutes and verify real host execution before opening the feature. GET/confirmation also attempt due cleanup. Availability expires immediately; physical removal uses cleanup and may need a retry after a filesystem failure.

**Owner decisions remain pending:** 3 or 5 completed feedback allowances/day, and 1 hour or 24 hours of image recovery availability. The questions have been presented separately. No answer is inferred. Example production limits/retention remain zero and the feature remains disabled. Disposable tests use a labelled 3-feedback/6-extraction/1-hour policy; this is not launch approval. An owner-approved external-processing notice/version and actual cleanup verification also precede collection. Payment-proof retention remains separate.

## Immutable correction and confirmation

Additive migration `014` creates handwriting pages and immutable transcription versions, then permits nullable `ai_operations.version_id` for image extraction and adds an optional owned handwriting binding. Existing writing/operation rows and foreign-key relationships remain intact; guarded schema changes follow existing native conventions. No production migration is run here.

Extraction returns a strict `{readable, text, uncertain, reason}` schema. An unreadable result must have empty text; no invented words or confidence percentages. Uncertain markers remain visible and must be corrected before confirmation. Model/student transcription versions append with hashes. Concurrent corrections use the saved transcription version; conflicting or duplicate request intent is checked with existing user locks and idempotent learning requests.

Confirmation accepts the owned saved transcription version and explicit acknowledgement, never an arbitrary text payload. It creates an immutable account-owned paragraph writing version and records its hash/version. Reconfirmation of the same wording creates no duplicate. Later correction invalidates confirmation; earlier writing and operation results remain available. Unsaved browser text disables evaluation in the UI, while the server independently requires the exact current confirmation and uses only its immutable writing version. Request retries cannot swap a version or spend a second allowance.

Browser transcription drafts are local, versioned and user-scoped. Reload restores input. A draft based on different current text requires review before adopting the new base. Upload images are memory-only before explicit submission. Keyed account components, abortable reads and before/after expected-user checks prevent stale account responses. Saved versions and previous feedback are linked to existing My Preparation and AI Usage rather than duplicate history systems.

## Shared provider and accounting

The experimental Mistral PR #77 was reviewed again. Its format guidance is useful, but it lacks immutable confirmation authority, refunds ambiguous failures, substitutes provider-specific models and writes fabricated zero token counts. It is not merged/imported.

Both extraction and feedback use the existing configurable primary Responses transport. Official [image-input guide](https://developers.openai.com/api/docs/guides/images-vision), [model page](https://developers.openai.com/api/docs/models/gpt-6-luna) and Responses input schema were rechecked on 7 October 2026. The public page advertises `gpt-6-luna` image input, and the API documents `input_image` with a base64 image URL. Actual account access, limits/billing, real handwriting accuracy and production-host behavior remain unverified; there is no connected live provider credential. No alternate model/provider is silently substituted.

Extraction sends only the normalized image and bounded instructions; confirmed feedback sends only the owned confirmed text. One TLS-verified official Responses POST, no retries/redirects/fallback/tools/full account history, `store:false`. This flag does not promise zero provider retention; the processing disclosure must describe the actual external service appropriately.

Two separate shared usage buckets:

- `handwriting_extract`: proposed hard cap of twice the chosen feedback allowance in accepted extraction attempts. Known unreadable/malformed/rejected results release the successful-use reservation but **still spend an accepted attempt**. This prevents unlimited paid extraction through repeated failures.
- `handwriting`: 3 or 5 successful feedback results/day once decided. Existing atomic reservation/success/failure rules apply; accepted attempts are capped at three times the allowance. Corrections/confirmation/reading/planning do not invoke a provider.

Both use the reservation's Asia/Karachi date, including completion across midnight/expiry. Account locks serialize reservations; dispatch claims once and releases all DB locks before network work. Unknown transport outcomes remain reserved. Known terminal failures release successful-use allowance but retain reported token/dispatch data. Valid findings are anchored to exact confirmed wording and stored atomically with successful accounting. General extraction-operation metadata omits a duplicate raw transcription. Missing image-token counts/pricing estimates remain null, not invented. Existing member/admin usage reports include the new scopes without exposing writing/images to general admin statistics.

Production readiness is fail-closed: handwriting enabled, AI approved/model verified, image capability verified, private provider credential, reviewed policy/version/notice, nonzero resolved limits/retention, actual supported image tools/private storage and cleanup verification. Defaults remain off. This does not authorize merging/deployment or change membership collection state.
